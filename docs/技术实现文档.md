# 技术实现文档 · 分层构建

> 这份文档讲**每一层是怎么从零搭起来的**，以及每一层里埋着哪些知识点和行业黑话。
> 不讲废话，只讲「做了什么 → 为什么这么做 → 这里面是什么知识」。
> 想直接跑起来：`python scripts/seed_db.py --reset && uvicorn app.main:app --port 8000`。

---

## 0. 全景：数据是怎么流动的

```
seed.py（确定性种子，24 个月业务数据）
 └─► L1 数据层    星型模型：5 维度 + 9 事实 + 2 系统表
      └─► L2 访问层    repositories（SQL 都写在这一层）
           └─► L3 业务层    services（口径、规则、事务边界）
                ├─► L4 接口层    FastAPI：鉴权 / 错误信封 / request_id / 限流
                │     └─► L5 表现层    零构建看板（HTML + CSS + 原生 JS）
                ├─► L6 SQL 层    20 个分析脚本（SQLite / MySQL 双跑）
                └─► L7 BI 层     Power BI（PBIP）/ Tableau（.twb）
                      └─► L8 Excel 层   明细 + SUMIFS + 静态透视 + VBA 宏

L9 验证层：pytest / 库存对账 / 跨方言比对 / BI 结构校验 —— 贯穿以上所有层
```

**分层的目的不是好看，是「改一处不牵动全局」**：换数据库只动 L1 的方言，换前端只动 L5，换 BI 工具不动后端一行代码。

| 层 | 目录 | 一行职责 | 出问题时的典型症状 |
|---|---|---|---|
| L1 | `app/db/models.py` | 数据长什么样 | 对账不平、外键报错 |
| L2 | `app/repositories/` | 怎么把数据取出来 | 慢查询、N+1 |
| L3 | `app/services/` | 业务规则怎么判 | 越权、脏数据、口径不一致 |
| L4 | `app/api/` | 对外怎么暴露 | 422/500 混着返回 |
| L5 | `web/` | 人怎么看见 | 图表糊、布局错乱 |
| L6 | `sql/` | 分析师怎么直接查 | 两个库结果不一致 |
| L7 | `bi/` | 业务方怎么自助取数 | 打开报错、字段对不上 |
| L8 | `excel/` | 非技术同事怎么拖透视 | 数字和看板不一致 |
| L9 | `tests/`、`scripts/_*.py` | 怎么证明上面都对 | 说不清哪一步错了 |

## L0 骨架：先把「配置」和「错误」两件事做干净

### 做法

1. `requirements.txt` 只留 6 个直接依赖：fastapi、uvicorn、sqlalchemy、pydantic、pydantic-settings、PyJWT、pymysql。
2. `app/core/config.py` 用 `pydantic-settings` 把所有可变项收进一个 `Settings` 类，从 `.env` 读。
3. 在 `Settings` 里加两个"自检"方法：`database_url` 的校验器只允许 `sqlite://` / `mysql+pymysql://`；`assert_runtime_ready()` 在 `ENV=prod` 时拒绝默认 JWT 密钥和 `CORS=*`。
4. `app/core/errors.py` 定义一棵异常树：`AppError` → `AuthError / PermissionError_ / NotFoundError / ConflictError / BusinessRuleError / RateLimitError / UpstreamError`，每类自带 HTTP 状态码和错误码字符串。
5. `app/main.py` 注册全局 exception handler，把任何异常压成统一信封。

### 解释

配置和错误处理是最容易被跳过、也最容易在出事时反咬一口的两层。把配置收进一个类，是为了让"哪些东西能改"变成一份可枚举的清单；把错误收成一棵树，是为了让前端只需要认 `error.code`，不用猜 HTTP 状态码背后的语义。

`assert_runtime_ready()` 这个设计值得单独说：默认 JWT 密钥留在代码里是最常见的上线事故，与其写文档提醒，不如让程序在启动时直接崩给你看。

### 知识点

| 知识点 | 具体是什么 |
|---|---|
| 12-Factor Config | 配置从环境变量注入，代码里不写死；`.env` 只用于本地 |
| pydantic-settings | 用类型注解声明配置，自动做类型转换和校验，`@field_validator` 可写自定义规则 |
| 错误信封设计 | `{"error": {"code", "message", "details", "request_id"}}`，让前端错误处理只有一个分支 |
| 快速失败 | 配置非法就在启动时抛异常，而不是等到第一个请求进来才 500 |

**黑话**：
- **魔法值（magic value）**：直接写死在代码里的常量，比如 `SECRET = "dev-secret"`。本项目把它变成"有名字的默认值 + 生产环境拒绝"。
- **契约（contract）**：前后端约定好的数据形状。错误信封就是一份契约。

## L1 数据层：先画维度，再填事实

### 做法

1. 定业务：B2B 工业零部件经销商，24 个月（2024-01-01 ~ 2025-12-31）。
2. **先建 5 张维度表**：`dim_date`(821 行)、`dim_product`(80)、`dim_customer`(60)、`dim_employee`(18)、`dim_supplier`(10)。
3. **再建 9 张事实表**：销售订单头 / 订单明细 / 采购单 / 库存快照 / 库存流水 / 线索商机 / 客服工单 / 营销投放 / AI 使用。
4. 每张表的主键都是自增整数（代理键），业务编号（`order_no`、`sku`）只做唯一约束。
5. 所有日期字段都存 `date_id`（形如 `20250115` 的整数），外键指向 `dim_date`。
6. 用 `random.Random(42)` 生成确定性数据：同一个种子跑两次，结果逐字节一致。
7. 生成完做一次**库存对账**：`期初建账 + 采购入库 − 销售出库 + 退货入库 − 报废 = 月末快照`，差异必须为 0。

### 解释

维度表先建，是因为事实表的所有外键都指向它们——顺序反了就得反复改 schema。日期维度单独抽表，是为了让"按月/按季/按年/按周"的汇总不用写日期函数，直接 join 取字段，两个数据库的写法才可能完全一致（SQLite 没有 `DATE_FORMAT`，MySQL 没有 `strftime`）。

代理键的意义是解耦：客户改名、SKU 重编码，都不影响历史事实表的关联。业务编号加唯一约束，是为了让"同一个订单号不能出现两次"这件事由数据库保证，而不是靠代码自觉。

确定性种子是**作品集的硬要求**：别人 clone 下来跑一遍，看到的必须是同一组数字，否则所有截图和文档里的结论都对不上。

### 知识点

| 知识点 | 具体是什么 | 本项目落点 |
|---|---|---|
| 星型模型 | 一张中心事实表 + 一圈维度表，join 只有一层 | 9 张事实各自挂到 5 张维度 |
| 雪花模型 | 维度再拆（品类挂品类组） | 不用：多了 join 层级，跨库写法更容易分叉 |
| 粒度（grain） | 一行代表什么 | 订单明细行 = 一个订单里的一个 SKU |
| 代理键 | 无业务含义的自增主键 | 所有 `*_id` |
| 退化维度 | 存在事实表里的维度属性 | `order_no`、`sku` 冗余在事实表便于排查 |
| 可加 / 半可加事实 | 金额可跨任意维度加总；库存余额只能按期取快照，跨时间相加无意义 | `fact_inventory_snapshot` 按 `date_id` 取月末 |
| SCD（缓慢变化维） | 维度属性变了怎么存：Type1 覆盖、Type2 加版本行 | 简化处理：`dim_product.unit_cost` 只存当前值，成本历史通过订单行的 `unit_cost` 快照保留 |
| 幂等种子 | 重跑不产生重复数据 | `run_seed(reset=True)` 先删后插 |

**黑话**：
- **事实表 / 维度表**：事实表存"发生了什么、多少"（可量化），维度表存"是谁、什么时候、在哪里"（描述性）。
- **口径**：一个指标的唯一定义。比如"营收 = `status='已完成'` 的 `net_amount` 之和，不含已取消、扣掉折扣"。口径不统一，四个工具就会算出四个数。
- **对账**：两套独立算法算同一个量，差异必须为 0。库存对账是本项目的数据质量底线。

## L2 数据访问层：ORM 只做翻译，不做业务

### 做法

1. `app/db/session.py` 用 `build_engine(settings)` 建引擎，SQLite 走 `check_same_thread=False`，MySQL 走连接池参数。
2. `session_scope()` 上下文管理器负责 commit / rollback / close；`get_db()` 作为 FastAPI 依赖，每个请求一个 Session。
3. `app/repositories/analytics_repo.py` 里每个函数对应一个分析问题（`kpis`、`sales_trend`、`funnel`、`rfm`…），返回 `list[dict]` 而不是 ORM 对象。
4. `scripts/export_schema.py` 从同一套 ORM 元数据导出 `sql/sqlite/schema.sql` 和 `sql/mysql/schema.sql`。

### 解释

仓储层返回 `dict` 而不是 ORM 实体，是为了让上层（service）和更上层（route）彻底不依赖 SQLAlchemy 的会话状态——对象一旦离开 Session 就处于游离态，属性访问会抛 `DetachedInstanceError`，这是新手最容易踩的坑。

DDL 从 ORM 导出而不是手写两份，是为了保证"代码里的表结构"和"SQL 文件里的表结构"永远一致。手写两份的结局一定是漂移。

### 知识点

| 知识点 | 具体是什么 |
|---|---|
| SQLAlchemy 2.0 风格 | `select(...).where(...)`，用 `Mapped[]` / `mapped_column()` 声明模型 |
| Session 生命周期 | 一个请求一个 Session，请求结束即关闭；不要跨请求复用 |
| N+1 查询 | 循环里逐条查关联表；用 `join` 或 `selectinload` 一次取回 |
| 事务边界 | `session_scope()` 里所有写操作要么全成功要么全回滚 |
| 方言（dialect） | SQLAlchemy 对不同数据库的适配层；`Integer` 在 SQLite 是 `INTEGER`，在 MySQL 是 `INT` |

**黑话**：
- **ORM**：对象关系映射。把表映射成类，把行映射成对象。好处是类型安全和防注入，代价是复杂查询不如手写 SQL 直观。
- **连接池**：预先建好一批数据库连接反复使用，避免每次请求都握手。SQLite 不需要（本地文件），MySQL 必须要。

## L3 业务层：口径和规则只能有一个出处

### 做法

1. `auth_service.py`：登录校验 → 签发 15 分钟访问令牌 + 7 天刷新令牌；刷新时**作废旧令牌并签新的**（轮换），登出时吊销。
2. `order_service.py`：建单前校验客户状态、商品在售状态、仓库可用库存；校验通过才落库，任一步失败整单回滚。
3. `insight_service.py`：8 条规则（`revenue_yoy`、`inventory_shortage`、`inventory_turnover`、`ai_lead_uplift`、`ai_ticket_uplift`、`ai_adoption`、`marketing_efficiency`、`customer_churn_risk`），每条输出 `title / detail / suggestion / severity / evidence_sql`。

### 解释

服务层存在的唯一理由：**同一套规则被多处调用时不能各写一遍**。比如"什么算低于安全库存"，在 KPI 卡、缺口清单、自动洞察里都要用，如果三处各写一遍 SQL，迟早有一处忘了处理 `on_hand_qty` 为空的情况。

`evidence_sql` 是本项目的一个态度：**结论必须可复现**。洞察说"8 个 SKU 低于安全库存"，下面就给一条能直接贴进 SQL 客户端跑出这 8 行的语句。这样"AI 说的"就变成了"你自己能验证的"。

### 知识点

| 知识点 | 具体是什么 |
|---|---|
| 业务规则下沉 | 规则写在 service，不写在 route（控制器只做参数解析）也不写在 repo（存取层只做取数） |
| 刷新令牌轮换 | 每次刷新都换新令牌并吊销旧的，被窃取的旧令牌只能用一次 |
| 事务边界 | `create_order` 的库存校验、扣减、写流水必须在同一个事务里，否则会超卖 |
| 阈值规则引擎 | 用代码写死的 `if` 而不是给业务配一堆可调参数——演示项目里可读性优先 |

**黑话**：
- **超卖**：库存 1 件卖出 2 件。根因通常是"先查后写"之间没有锁或事务。
- **可复现性（reproducibility）**：别人拿到你的项目，跑出同样的结果。数据项目里这比"模型多准"更重要。

## L4 接口层：把"能跑"变成"可运维"

### 做法

1. 路由分三组：`/api/auth/*`（4 个）、`/api/dashboard/*` + `/api/analytics/*` + `/api/ai/*`（12 个）、`/api/{products,customers,sales-orders,inventory}`（6 个）。
2. `deps.py` 提供三件套：`get_current_user`（解析 Bearer 令牌）、`require_permission("write")`（RBAC 校验）、`pagination`（统一分页参数）。
3. 中间件：生成 `request_id` 塞进 contextvar → 写结构化 JSON 访问日志 → 对 `/api` 做令牌桶限流。
4. 所有响应都有 Pydantic 模型，OpenAPI 文档自动生成在 `/docs`。

### 解释

把鉴权做成"依赖"而不是"装饰器"，是因为 FastAPI 的依赖注入可以组合：`require_permission("write")` 内部先调 `get_current_user`，路由函数只管业务，签名里多一行 `_user: SysUser = Depends(...)` 就完成了权限声明。

`request_id` 贯穿的价值在排障：日志里每条都带同一个 id，用户报"我点了没反应"，给他 id 就能捞出这一个请求经过的所有日志。

### 知识点

| 知识点 | 具体是什么 |
|---|---|
| 依赖注入 | 路由声明"我需要什么"，框架负责构造；可嵌套、可复用、可覆盖测试 |
| RBAC | 角色 → 权限集合的映射：`admin{read,write,analytics,admin}`、`analyst{read,analytics}`、`sales{read,write}`、`viewer{read}` |
| 令牌桶限流 | 桶按速率补令牌，取不到就 429；比固定窗口平滑 |
| contextvar | 异步环境下的"线程局部变量"，用来传递 request_id 而不必层层传参 |
| 结构化日志 | 输出 JSON 而非纯文本，便于 ELK/Loki 检索 |

**黑话**：
- **可观测性（observability）**：系统出问题时能不能靠日志、指标、链路自己说清楚发生了什么。
- **422 vs 400**：422 是"格式对但语义不合法"（字段长度不够），400 是"请求本身有问题"。混用会让前端没法区分该不该重试。
- **限流（rate limit）**：主动拒绝部分请求保护系统，返回 429 并带 `Retry-After`。

## L5 表现层：零构建，但要把布局做对

### 做法

1. 只有一个 `index.html` + 一个 `styles.css` + 一个 `app.js`，不打包、不编译。
2. 布局用 CSS Grid 固定两栏：`.app { grid-template-columns: 252px 1fr; height: 100vh }`，`body` 和侧边栏都不滚动，**只有 `.content` 内部滚动**。
3. 令牌只放内存（`state.accessToken`），刷新页面即失效。
4. 图表按数据特征选实现：折线用 SVG（需要路径和渐变），横向条形和漏斗用 HTML/CSS（文字永远是 12px 不会被缩放）。
5. 渲染前先量出容器宽度（`contentWidth()` / `colWidth()`），按 1:1 坐标系画图，避免 viewBox 等比缩放把字号压小。
6. 静态资源带版本号 `?v=6`，改完样式必须改版本号才能绕过浏览器缓存。

### 解释

**侧边栏"半截"是怎么来的**：旧版用 `position: sticky; height: 100vh`，sticky 只在视口内吸附，页面整体很长时侧边栏看起来只有一屏高。正确做法是把滚动交给内容区：外层 `overflow: hidden` + 侧边栏 `height: 100vh`，内容区 `flex: 1; overflow-y: auto`。这样侧边栏永远占满左侧，滚动条只出现在右侧。

**为什么条形图不用 SVG**：SVG 设 `width: 100%` 加固定 `height` 时会被浏览器等比缩放，`font-size: 10` 的文字在窄容器里会被压到 5px。HTML/CSS 的条形不受这个影响，文字永远是设定的像素值。

### 知识点

| 知识点 | 具体是什么 |
|---|---|
| CSS Grid 布局 | `grid-template-columns` 定义列轨道；`minmax(0, 1fr)` 防止内容撑破 |
| 视口单位 100vh | 等于视口高度；配 `overflow: hidden` 可做"应用式"布局 |
| SVG viewBox 缩放陷阱 | `preserveAspectRatio` 会按比例缩放一切，包括描边和文字 |
| 渐进增强 | 先保证不用框架也能跑，再考虑加交互 |
| 缓存击穿 | 改了 CSS 但浏览器用旧缓存；用 `?v=N` 或 hash 文件名强制失效 |

**黑话**：
- **首屏（above the fold）**：不滚动就能看到的内容，决定第一印象。
- **设计系统**：颜色、间距、字号、圆角统一成一组变量（本项目全在 `:root` 里）。
- **零构建**：不经过 webpack/vite，浏览器直接跑源码。牺牲工程化能力，换取"双击就能看"。

## L6 分析 SQL 层：20 个问题，两套方言，一套结果

### 做法

1. `sql/sqlite/analysis/01..20_*.sql` 是**源版本**，每个脚本顶部写清业务问题，底部写 `-- 预期结果：` 并把真实输出贴回来。
2. `scripts/sqlite_to_mysql.py` 做正则方言转换，生成 `sql/mysql/analysis/`（**禁止手改**）。
3. `scripts/_run_sql_analysis.py` 分别用 sqlite3 和 pymysql 跑同一批脚本。
4. `scripts/_compare_sql_dialects.py` 逐值比对，三档判定：`exact`（相对误差 < 1e-6）、`tolerable`（< 5e-3 或绝对差 < 0.5）、`diff`（真不一致）。
5. `scripts/_gen_sql_verification.py` 生成 `sql/_验证结果.md`（脚本清单 + 行数/列数 + 一致性结论）。

### 解释

20 个脚本覆盖的是数据分析师面试真正会问的东西：同比环比、帕累托与 ABC、RFM、流失预警、漏斗转化、CAC/ROAS、库存周转、收发存对账、移动平均预测。

**跨方言是这层最大的坑**，也是最能体现功力的一段。SQLite 和 MySQL 的差异分三类：

| 类型 | SQLite | MySQL 8 |
|---|---|---|
| 日期格式化 | `strftime('%Y-%m', d)` | `DATE_FORMAT(d, '%Y-%m')` |
| 日期差 | `julianday(a) - julianday(b)` | `DATEDIFF(a, b)` |
| 字符串拼接 | `a \|\| b` | `CONCAT(a, b)` |
| 行内取大/小 | `MAX(a, b)`（标量版） | `GREATEST(a, b)` |
| 类型转换 | `CAST(x AS INTEGER)` | `CAST(x AS SIGNED)` |
| `SELECT *, 表达式` | 允许 | 不允许，要写 `表.*` |

还有一类更隐蔽的：**精度**。MySQL 的 `div_precision_increment=4` 会让除法结果多出小数位，`AVG(DECIMAL)` 保留 4 位小数，而两库对 `SUM(DOUBLE)` 的累加顺序不同。所以有 5 个脚本的末位数字对不上——这不是 bug，是浮点累加顺序的必然结果。处理方式是：转换器把 `AVG(x)` 改写成 `AVG(CAST(x AS DOUBLE))`，比对器给一个 5e-3 的容差档，并在文档里写清根因。

另外三处是**确定性改造**：`NTILE(4) OVER (ORDER BY r_days DESC)` 在并列时行序不确定，必须加 `customer_id` 当 tiebreaker；多列 `ORDER BY` 也要补唯一键，否则两库返回的行序可能不同。

### 知识点

| 技能 | 用在哪 |
|---|---|
| CTE（`WITH`） | 把多层聚合拆成可读的步骤，04 号 RFM 分了 base → rfm → 打分三层 |
| 递归 CTE | 20 号补全月份序列（`WITH RECURSIVE months(n) AS (...)`） |
| 窗口函数 `RANK/ROW_NUMBER` | 02 号商品排名、07 号维度内排名 |
| `NTILE(4)` | 04 号 RFM 四等分位 |
| `LAG` | 01 号环比、05 号流失预警（距上次购买天数） |
| `SUM() OVER (ROWS BETWEEN ...)` | 20 号移动平均 |
| 条件聚合 `SUM(CASE WHEN ...)` | 漏斗各阶段计数一次扫表搞定 |
| 日期序列补齐 | 没有订单的月份也要出现，否则趋势图会断 |

**黑话**：
- **同比 / 环比**：同比 = 和去年同月比（消除季节性），环比 = 和上个月比（看短期动量）。
- **帕累托 / ABC 分类**：80% 的销售额来自 20% 的商品；A 类累计贡献前 80%，B 类 80~95%，C 类剩下。
- **RFM**：Recency（最近一次购买）、Frequency（频次）、Monetary（金额），三维打分做客户分层。
- **CAC / ROAS**：CAC = 获客成本 = 投放花费 ÷ 线索数；ROAS = 投放回报 = 归因收入 ÷ 花费，大于 1 才不亏。
- **周转天数**：库存金额 ÷ 日均销货成本，数字越大说明货压在仓库里越久。
- **动销 / 呆滞**：动销 = 近 N 天有出库；呆滞 = 有库存但长期不动。
- **安全库存**：为防止断货预留的最低库存水位。
- **赢率（win rate）**：成单数 ÷ 商机总数。
- **口径漂移**：同名字段在两个系统里定义不同，导致报表对不上。

## L7 BI 层：交付的是工程文件，不是说明书

### 做法

**Power BI（PBIP 项目格式，可用文本编辑）**

1. `bi/powerbi/ERP经营分析.pbip` → 指向 `.SemanticModel` 和 `.Report` 两个目录。
2. `model.tmdl`：11 张表、175 列、30 个度量、15 条关系（维度 1 → 事实 *，单向筛选）。
3. `report.json`：2 页报表，视觉对象位置和字段绑定全部写进 JSON。
4. `verify_pbip.py` 做 7 项结构校验：文件是否齐全、TMDL 语法、关系两端表列是否存在、度量引用是否成立、M 分区类型列表是否合法。

**Tableau（.twb + .twbx）**

1. `build_twb.py` 生成 XML：11 个数据源（与 11 个 CSV 一一对应）、10 个 worksheet、3 个 dashboard。
2. 32 个计算字段（`calcs.md` 由脚本从 twb 自动提取，不手写）。
3. `.twbx` 是把 twb 和 CSV 打包成 zip，CSV 必须无 BOM 否则 Tableau 会把首列名读成 `\ufeffxxx`。

### 解释

为什么不交截图或"操作说明"？因为**能不能打开**是硬门槛。BI 工具的核心能力不在拖控件，在语义模型：关系方向错了，`CALCULATE` 出来的数就是错的，而这种错误在截图里看不出来。

`verify_*.py` 的存在也是同一个逻辑：`.twb` 是 XML，`.pbip` 是 TMDL，两者都可能因为一个引号少一半而打不开。用脚本校验结构，比反复用桌面软件点开试要快得多。

### 知识点

| 知识点 | 具体是什么 |
|---|---|
| 语义模型 | 表 + 关系 + 度量 + 层次结构，BI 工具的计算基础 |
| 关系方向 | 维度表（1）→ 事实表（*），单方向筛选；双向筛选会造成歧义和循环 |
| DAX 计算上下文 | 行上下文（当前行）+ 筛选上下文（当前切片）；`CALCULATE` 的作用是改写筛选上下文 |
| `DIVIDE` 而非 `/` | 自动处理除零 |
| 时间智能 | `DATEADD`、`DATESYTD`、`SAMEPERIODLASTYEAR` 依赖一张连续且标记为日期表的 `dim_date` |
| `REMOVEFILTERS` | 在度量里临时移除某个维度筛选，算"占全部的比例"时必用 |
| Tableau LOD | `{FIXED [dim]: SUM([x])}` 在指定维度上计算，不受视图筛选影响 |
| 表计算 | `RUNNING_SUM`、`LOOKUP`、`TOTAL`，与"计算字段"的区别是它依赖视图里的行顺序 |

**黑话**：
- **度量值 vs 计算列**：度量值在查询时按当前上下文算（不占存储），计算列在刷新时逐行算好存起来（占存储）。
- **上下文转换**：在行上下文里调用度量值，行上下文会自动变成等价的筛选上下文。
- **Extract（.hyper）**：Tableau 把数据抽成列式文件加速查询；本项目的 `.twbx` 直接把 CSV 打进去。
- **增量刷新**：只刷新新增分区，全量刷新太慢时的常规手段。

## L8 Excel 层：三层结构，各司其职

### 做法

1. `build_workbook.py` 用 openpyxl 生成 18 个 sheet：说明 / 字段字典 / 7 张事实明细 / 4 张维度 / 透视预分析 / 4 个静态透视结果。
2. 第二层是 `SUMIFS` 公式：把明细按"月份 × 维度"汇总，改明细数字会自动重算。
3. 第三层是静态预聚合值：环境打不开透视表时的兜底。
4. `pivot_macro.bas` 提供 `BuildAllPivots` 宏（GBK 编码 + CRLF，否则 VBA 编辑器里中文变乱码），一键生成 8 张真透视表，并用 `VerifyAgainstStatic` 和静态页对账。

### 解释

本机 Office 许可过期时，COM 自动化（`Excel.Application`）直接抛"许可已过期"，`Range.Value2` 写入和 `SaveAs` 全部失败。所以改成"静态值 + 公式 + 宏"三层：静态值保证任何环境都能看，公式保证改数能重算，宏保证在正常环境下能生成可交互的透视表。

这也顺带解释了 `.bas` 为什么必须是 GBK：VBA 编辑器按系统 ANSI 代码页读文件，UTF-8 的中文字符串会变成乱码，宏一运行就报"语法错误"。

### 知识点

| 知识点 | 具体是什么 |
|---|---|
| `SUMIFS` 多条件聚合 | `SUMIFS(值列, 条件列1, 条件1, 条件列2, 条件2)`，Excel 里最接近 SQL `GROUP BY` 的写法 |
| 透视表缓存 | 透视表读的是内存里的 pivot cache，源数据变了要手动刷新 |
| 切片器 / 日程表 | 透视表的可视化筛选器，比字段下拉直观 |
| openpyxl | 纯 Python 读写 xlsx，不需要装 Office；但不能计算公式，只能写公式 |
| VBA 编码 | `.bas` 用系统 ANSI（中文 Windows 是 GBK），行尾 CRLF |

**黑话**：
- **预聚合**：提前把明细算成汇总表，查询时直接读结果。代价是失去下钻能力，收益是快。
- **明细 vs 汇总**：明细表回答"具体是哪几单"，汇总表回答"一共多少"。BI 里两者都要有。

## L9 验证层：怎么证明上面九层都是对的

### 做法

1. `pytest` 29 个测试：认证（登录/刷新轮换/登出吊销）、权限（viewer 不能建单）、业务（库存不足整单回滚）、口径（KPI 与 SQL 脚本一致）。
2. 库存对账断言：净流水 = 月末快照，差异必须为 0。
3. 跨方言比对：20 个脚本 × 2 个数据库，逐值判定。
4. BI 结构校验：`verify_pbip.py`(7 项)、`verify_twb.py`(6 项)。
5. `bi/verify_baselines.py` 核对 BI 里的基线数字和数据库一致。

### 解释

测试的重点不是覆盖率，是**把"我以为对"变成"能证明对"**。比如 KPI 卡显示营收 3775 万，SQL 脚本 01 号跑出同样的数字，两边都跑在同一个库上——这才叫口径统一。再比如 `.twb` 里 32 个计算字段引用的列名，必须和 CSV 表头逐字一致，靠人眼看是不可能看完的。

### 知识点

| 知识点 | 具体是什么 |
|---|---|
| 夹具（fixture） | `conftest.py` 里会话级 fixture，建库 + 灌数只做一次 |
| 契约测试 | 断言响应结构而不只是状态码 |
| 黄金样本 | 固定输入 → 固定期望输出，任何改动导致偏差就报警 |
| 容差判定 | 浮点比较不能用 `==`，要给相对/绝对误差阈值 |
| 结构校验 | 对 XML/JSON 文件做 schema 级检查，比"打开看看"可靠 |

**黑话**：
- **回归**：改了 A 把 B 弄坏了。回归测试就是防止这件事。
- **冒烟测试（smoke test）**：只验证主流程能跑通的最小测试集。

## 11. Windows 一键启动：`启动网站.bat`

### 为什么需要它

`uvicorn app.main:app --port 8000` 本身只有一行，但对不熟悉终端的人有三个真实的坑：

1. **必须在项目根目录执行**——在 `web\` 或 `scripts\` 子目录里敲 `.\scripts\run.ps1`，PowerShell 会直接报 `无法将 ... 识别为 cmdlet`；
2. **PowerShell 默认禁止运行 `.ps1`**——需要改执行策略，很多人卡在这一步；
3. **服务窗口被误关**——网站随即打不开，用户以为是"网站坏了"。

所以交付一个双击即可的 `.bat`，把「切目录 → 查服务 → 起服务 → 开浏览器」四件事封装掉。

### 执行流程

```text
双击 启动网站.bat
  ├─ cd /d "%~dp0"                     切到脚本所在目录（解决坑 1）
  ├─ curl /health 探测 8000 端口
  │    ├─ 200 → 已在运行，直接开 Edge（幂等，不会起第二个服务）
  │    └─ 失败 → 检查 python → 新窗口起 uvicorn
  ├─ 每秒重试 /health，最多 20 次
  ├─ 用 Edge 完整路径打开；找不到则退回默认浏览器
  └─ 窗口停留 8 秒，显示地址与账号
```

### 关键代码

```bat
@echo off
setlocal EnableExtensions
rem 关键：以脚本自身所在目录为工作目录
cd /d "%~dp0"
set "URL=http://127.0.0.1:8000"
set "SYS=%SystemRoot%\System32"
set "EDGE=%ProgramFiles(x86)%\Microsoft\Edge\Application\msedge.exe"

rem 服务已在运行则直接打开浏览器（幂等）
"%SYS%\curl.exe" -sf -o nul --max-time 2 "%URL%/health" >nul 2>&1
if not errorlevel 1 goto open

python --version >nul 2>&1
if errorlevel 1 ( echo 未检测到 Python & pause & exit /b 1 )

rem 新窗口启动服务，/k 保证窗口不自动关闭
start "ERP Server" cmd /k "python -m uvicorn app.main:app --host 127.0.0.1 --port 8000"

rem 最多等 20 秒，每秒探测一次
for /l %%i in (1,1,20) do (
    "%SYS%\curl.exe" -sf -o nul --max-time 1 "%URL%/health" >nul 2>&1
    if not errorlevel 1 goto open
    "%SYS%\timeout.exe" /t 1 /nobreak >nul
)
echo 启动超时，请查看 ERP Server 窗口 & pause & exit /b 1

:open
if exist "%EDGE%" ( start "" "%EDGE%" "%URL%" ) else ( start "" "%URL%" )
"%SYS%\timeout.exe" /t 8 /nobreak >nul
```

实际文件比上面多几行提示文案，逻辑一致；账号密码以 README 账号表为准，脚本只负责打印。

### 解释

**为什么用 `%~dp0`**：批处理里的 `%~dp0` 展开为脚本自身所在目录（带尾部反斜杠）。先 `cd /d` 过去，双击时无论当前目录是什么都能找到 `app/` 和 `data/erp.db`，这是对坑 1 的根治。

**为什么健康检查失败就 `goto open` 而不是重启服务**：`curl -sf` 在 HTTP 4xx/5xx 或连接失败时返回非 0，`if not errorlevel 1` 即"探测成功"。服务已在运行时再起一个 uvicorn 会报 `address already in use`，用户看到红字就以为坏了——所以先探测、后启动，保证脚本可重复执行（幂等）。

**为什么全部写绝对路径**：`%SystemRoot%\System32\curl.exe`、`%SystemRoot%\System32\timeout.exe`。最初版本用 `powershell -Command` 做探测，在 PATH 不完整的终端里直接报"找不到 powershell"，脚本第一行就崩。系统目录变量在 Windows 上永远存在，比 PATH 可靠。

**为什么用 `start "ERP Server" cmd /k`**：`start` 另开窗口，`/k` 让命令结束后窗口保留（崩溃时能看到报错）。如果把 uvicorn 放在同一窗口前台跑，启动器就没法继续执行"打开浏览器"了；用 `start /b` 后台跑则会随父窗口关闭而被回收。

**为什么文件必须是 GBK + CRLF**：中文 Windows 的 cmd 默认代码页是 936。若文件存成 UTF-8，中文提示会乱码；若只有 LF 换行，cmd 解析多行 `if (...)` 块和 `goto` 标签时会错位，典型报错是 `'xxx' 不是内部或外部命令`。所以生成后用 Python 转一次：`p.write_text(s, encoding="gbk", newline="\r\n")`。用记事本二次编辑时，另存为要选 **ANSI**。

### 排错表

| 现象 | 原因 | 处理 |
|---|---|---|
| `无法将 .\scripts\run.ps1 识别为 cmdlet` | 当前目录在 `web\` 等子目录 | `cd ..` 回根目录，或直接双击 `启动网站.bat` |
| `禁止运行脚本` / `UnauthorizedAccess` | PowerShell 执行策略 | 不改系统设置，改用 `.bat`；或 `powershell -ExecutionPolicy Bypass -File .\scripts\run.ps1` |
| 黑窗口一闪而过 | 脚本内报错后立即退出 | 在根目录打开 cmd 手动执行 `启动网站.bat`，看完整报错 |
| 提示 `address already in use` | 8000 端口已有服务 | 关闭旧的 `ERP Server` 窗口；或改脚本里的端口与 `--port` |
| 中文提示乱码 | 文件被存成 UTF-8 | 记事本另存为 ANSI，或重新用 Python 转 GBK |
| 网站打开但图表空白 | 只开了静态文件、没起后端 | 必须通过 `http://127.0.0.1:8000` 访问，不能双击 `web/index.html` |

### 知识点

| 知识点 | 具体是什么 |
|---|---|
| `%~dp0` | 批处理内置变量：脚本所在驱动器和路径 |
| `errorlevel` | 上一条命令的退出码；0 为成功，`if not errorlevel 1` 即判断成功 |
| 幂等启动 | 先探测再启动，重复执行不产生第二个服务 |
| `start` / `cmd /k` | 新开窗口并保持不关闭；适合"服务窗口 + 启动器窗口"分离 |
| 代码页 936 | 中文 Windows 默认 GBK；跨编码保存会导致乱码或语法错位 |
| 绝对路径兜底 | 不依赖 PATH，避免"在我机器上能跑" |

**黑话**：
- **幂等（idempotent）**：执行一次和执行十次结果一样。启动脚本必须幂等，否则第二次双击就端口冲突。
- **冒烟启动**：不跑测试，只确认"服务能起来、首页能打开、登录能成功"。
