# 数据字典与业务口径（唯一口径来源）

> 本文件是 SQL 脚本、Excel 透视表、Power BI / Tableau 报表、AI 产品销售论证的**共同口径来源**。
> 表结构由 `app/db/models.py` 定义，DDL 由 `scripts/export_schema.py` 导出，任何口径调整都要回写模型再重新导出。

## 1. 业务背景

一家工业自动化零部件的 B2B 经销商（自用演示数据），经营 24 个月（2024-01-01 ~ 2025-12-31），
数据覆盖销售、进销存、采购、线索商机、客服工单、营销投放与 AI 助手使用记录。

| 维度 | 取值 |
|---|---|
| 客户分层 | A（10 家）/ B（20 家）/ C（30 家），A 类客单高、折扣深 |
| 销售渠道 | 直销 / 经销 / 电商 / OEM |
| 获客来源 | 官网 / 展会 / 转介绍 / 广告投放 / 电话外呼 / 内容营销 |
| 行业 | 智能制造 / 汽车零部件 / 医疗器械 / 电子代工 / 新能源 / 食品饮料 / 化工 / 物流仓储 |
| 区域 | 华东 / 华南 / 西南 / 华北（华东仓服务华东、华南、华北；西南仓服务西南） |
| 订单状态 | 已完成 95% / 已退款 1.5% / 处理中 1.7% / 已取消 1.8% |
| 付款状态 | 已付 / 部分付款 / 未付款 |

## 2. 表结构

### 维度表
| 表 | 主键 | 说明 |
|---|---|---|
| `dim_date` | date_id (YYYYMMDD) | 日期维表，含 year/quarter/year_month/year_quarter/week_of_year/day_of_week/is_weekend；覆盖业务窗口 + 尾部 90 天（承载交付日期） |
| `dim_employee` | employee_id | 姓名、团队 team、角色 role、区域、入职日期 |
| `dim_supplier` | supplier_id | 供应商、区域、货期 lead_time_days、评级 rating |
| `dim_product` | product_id | SKU、品类 category、品牌、计价单位、单位成本 unit_cost、标价 list_price、供应商、状态（在售/停产） |
| `dim_customer` | customer_id | 名称、行业、区域、城市、分层 tier、渠道、获客来源、合同日期、客户经理、合同额、状态 |

### 事实表
| 表 | 主键 | 说明 |
|---|---|---|
| `fact_sales_order` | order_id | 订单主表：客户、销售员、订单日、交付日、渠道、状态、付款状态、gross_amount（吊牌额）、discount_amount（折扣额）、net_amount（实收）、cost_amount、gross_profit、delivery_days、is_return |
| `fact_sales_order_item` | order_item_id | 订单明细：product_id、qty、unit_price、discount_rate、revenue_amount、cost_amount |
| `fact_purchase_order` | purchase_id | 采购单：供应商、商品、下单日、到货日、数量、金额、状态（在途/已入库/已取消） |
| `fact_inventory_transaction` | txn_id | 库存流水：txn_type ∈ {期初建账, 采购入库, 销售出库, 退货入库, 报废}，qty 正数入库负数出库，ref_no 关联单据 |

## 3. 关键指标口径（所有报表必须一致）

| 指标 | 口径 |
|---|---|
| 营收（net revenue） | `net_amount` 求和，仅统计 `status = '已完成'`；**已退款订单不计入营收** |
| 吊牌额 / 标价额 | `gross_amount` 求和（含折扣前） |
| 折扣额 | `discount_amount` 求和；折扣率 = 折扣额 / 吊牌额 |
| 成本 | `cost_amount` 求和 |
| 毛利 | `gross_profit` 求和；毛利率 = 毛利 / 营收 |
| 客单价 AOV | 营收 / 订单数（仅已完成订单） |
| 订单数 | `fact_sales_order` 行数（仅已完成） |
| 客户数 | `COUNT(DISTINCT customer_id)` |
| 毛利率（商品级） | (revenue_amount − cost_amount) / revenue_amount |
| 动销率 | 有销售的 SKU 数 / 在售 SKU 数 |
| 库存周转天数 | 期末库存金额 ÷ 日均销售成本（成本口径，不用售价） |
| 缺货率 | `on_hand_qty < safety_stock` 的 SKU 数 ÷ SKU 总数 |
| 滞销 SKU | 近 90 天无销售且库存 > 0 的 SKU |
| 帕累托贡献 | 商品销售额降序累计占比 ≥ 80% 的商品数量占比 |
| RFM | R = 距最近一次成交天数；F = 期间成交次数；M = 期间成交金额；分档用四分位 |
| 线索转化率 | 某阶段及以后的数量 ÷ 该阶段的数量（漏斗逐级转化） |
| 成单率 | `stage = '成单'` 数量 ÷ 线索总数 |
| AI 辅助商机赢率 | ai_assisted=1 的平均 win_probability；对照组 ai_assisted=0 |
| AI 提效（工单） | AI 处理 vs 人工处理的 first_response_minutes / satisfaction / converted_to_opportunity |
| AI 采纳率 | `accepted_count / query_count` |
| AI 节省工时 | `minutes_saved` 求和（小时 = ÷60） |
| CAC | 渠道成本 ÷ 线索数；ROAS = 归因收入 ÷ 成本 |
| 同比 / 环比 | 同比 = 与去年同期比；环比 = 与上一期比。月份粒度用 `year_month` |

## 4. 数据内置的业务规律（用于验证分析结论是否成立）

1. **季节性**：12 月最高、2 月最低（春节），Q4 明显高于 Q1。
2. **年度增长**：2025 营收高于 2024 约 15%~18%。
3. **分层差异**：A 类客户客单价最高、折扣率最高、贡献营收占比最大。
4. **AI 价值**（可直接用 SQL 验证，是「AI 产品销售思考」的量化底座）：
   - AI 辅助商机成单率、赢率高于对照组，销售周期更短；
   - AI 处理工单首次响应更快、满意度更高、转商机率更高；
   - 内部 AI 助手采纳率约 58%~92%，累计节省工时可观。
5. **库存可对账**：期初建账 + 采购入库 + 退货入库 − 销售出库 − 报废 = 月末快照（差异为 0）。

## 5. 使用约束

- 任何分析先过滤业务窗口：`dim_date.full_date BETWEEN '2024-01-01' AND '2025-12-31'`（维度表尾部日期仅用于交付日期）。
- 营收相关指标一律排除 `已退款`；库存与采购指标不受订单状态影响。
- 不要把「已取消」订单计入订单数与营收。
- 所有结论必须能回溯到具体 SQL 脚本或 BI 报表，不接受手工估算。

## 6. 跨数据库一致性（SQLite ↔ MySQL 8）

同一套 SQL 有两个方言版本（`sql/sqlite/analysis/` 与 `sql/mysql/analysis/`），
MySQL 版由 `scripts/sqlite_to_mysql.py` 从 SQLite 版**自动转换**生成，因此逻辑完全等价。

### 6.1 验证结论

`scripts/_compare_sql_dialects.py` 把两个版本分别执行后逐行逐列比对：

- **15 个脚本逐值完全一致**（列名、行数、每一个单元格）
- **5 个脚本存在末位精度差异**（共 13 处），全部属于**引擎数值语义差异**，不是口径差异

### 6.2 末位精度差异的三类根因

| 现象 | 根因 | 涉及脚本 |
|------|------|---------|
| `stockout_rate` 0.0437 vs 0.0438、`cac` 839.91 vs 839.92 | MySQL 的 `div_precision_increment` 默认 = 4，`DECIMAL` 除法结果先被截断到 4 位小数，再被外层 `ROUND` 二次处理；SQLite 走 IEEE754 双精度除法 | 11、18 |
| `avg_delivery_days` 12.13 vs 12.12、`avg_resolution_hours` 7.03 vs 7.04 | MySQL 的 `AVG(DECIMAL)` 结果 scale = 4，SQLite 的 `AVG(REAL)` 保留完整浮点精度 | 08、17 |
| `hours_saved` 51.0 vs 50.9 | 浮点累加顺序不同（两库 `SUM(DOUBLE)` 遍历顺序不同），在 `.x5` 舍入边界上差 1 个末位单位 | 19 |

> **这是有意保留的差异**：把它抹平会让 SQL 失去对底层引擎语义的表达力。
> 真实数据仓库里 SQLite 与 MySQL 并存是常态，
> 能说清「为什么这个数会差 0.01」比假装两边永远一样更接近生产实际。
>
> 需要**完全一致**时：MySQL 侧显式写 `AVG(CAST(x AS DOUBLE))` 与 `CAST(x AS DOUBLE) / y`
> （转换器已对 AVG 自动处理），或把 `div_precision_increment` 调大。

### 6.3 为保证可复现而做的确定性改造

以下三处是**先在 MySQL 上跑出不一致、再回头修的**，属于真实踩坑：

| 位置 | 问题 | 修法 |
|------|------|------|
| 04 号 RFM | `NTILE(4)` 在存在并列值时，档位边界取决于输入行序，两库分位结果不同 | 分位排序追加 `customer_id` 作为唯一 tiebreaker |
| 04 号 RFM | `ORDER BY rfm_score DESC, m_amount DESC` 存在并列，最终排序不稳定 | 追加 `customer_id` 作为最终 tiebreaker |
| 18 号 CAC/ROAS | 同一渠道有 24 个月数据，`ORDER BY scope, scope_value` 并列严重 | 追加 `scope_month` 作为第三排序键 |

> **通用教训**：窗口函数与排序在多行并列时，**必须显式指定唯一 tiebreaker**，
> 否则会出现「同一份数据、两个引擎、两个结果」，且无法复现。

见 `scripts/_verify_mysql_instance.md`（用本机 MySQL 8 或 Docker 建临时实例跑比对）。
